# 009 — Живой поток serverinfo: онлайн и время мира одним SSE-соединением

Цель: лендинг получает `total_online`, `max_online` и `world_time` одним
соединением `GET /v1/serverinfo/stream`, без опроса раз в несколько секунд и без
токена. Два готовых RPC (`/v1/serverinfo/totalonline`, `/v1/serverinfo/worldtime`)
остаются как есть.

## Что меняется

| Где | Было | Стало |
| --- | --- | --- |
| `GET /v1/serverinfo/stream` | нет маршрута | SSE-поток, публичный, без параметров |
| `internal/serverinfo/.../stream.go` | нет файла | hub + poller + `ServeHTTP`/`Run` |
| `internal/serverinfo/fx.go` | сервис и sweeper | плюс `StreamHandler` и его `fx.Invoke` |
| `internal/server/app.go`, `server.go` | архив модов как единственный plain-HTTP маршрут | плюс поток через `mux.HandlePath` |
| `internal/server/httplog.go` | одна запись `http.call.finish` | поток пишет `http.call.stream.finish` с `connection_ms` |

## Топология

```
Игровой мод (писатель)  →  MongoDB: serverinfo (singleton, 5 с)
                                │
                                └─ FindOne раз в 5 с
vsservice (Go)
  ├─ Stream (один на процесс)
  │    ├─ Run(ctx): poll → publish только при изменении
  │    ├─ subscribers: map[chan []byte]struct{}, буфер 8 кадров
  │    └─ ServeHTTP: заголовки, retry, кадры, ": ping" через 25 с
  └─ sweeper: гасит протухший total_online (без изменений)
```

Один подписчик стоит горутины и сокета. Один опрос стоит одного `FindOne` на
1000 подписчиков, а не 1000.

## Контракт

- Ответ: `200`, `Content-Type: text/event-stream; charset=utf-8`,
  `Cache-Control: no-store`, `X-Accel-Buffering: no`.
- Первый кадр — сразу после подписки, из текущего снимка; дальше по кадру на
  каждое изменение:

  ```
  event: serverinfo
  data: {"online":12,"max_online":100,"time":"Day 45 14:20"}
  ```

- `retry: 5000` отдельным кадром перед первым событием.
- `": ping"` — комментарий после 25 с тишины: клиент его не видит, прокси не
  закрывает соединение.
- Больше 1000 подписчиков: `503` и `Retry-After: 10`.
- Клиент, который не читает, отключается: очередь переполнилась — канал
  закрывается; зависшая запись обрывается по `write timeout` 10 с.

Имена полей (`online`, `max_online`, `time`) — те же, что отдают два RPC под
`UseProtoNames`. Это замороженный контракт: лендинг уже его потребляет.

## Решения и почему так

- **Hub живёт в процессе, а не в Mongo.** Change streams требуют replica set, а
  кластер развёрнут как standalone: подписка на изменения документа невозможна.
  Tailing-курсор (`OpTime`) на standalone тоже не работает. Опрос документа раз
  в 5 с стоит один дешёвый `FindOne` по `_id`+первичному индексу и не требует
  менять развёртывание.
- **NATS не возвращается.** `nats_guard_test.go` в корне падает, если брокер
  вернётся; 008 удалил его осознанно, и поток serverinfo — не повод его
  восстанавливать.
- **Ограничение «одна реплика».** Снимок и подписчики живут в памяти одного
  процесса. Две реплики за балансировщиком дают каждому клиенту свой поток и
  свой опрос — данные при этом верные (источник один, `serverinfo`), но
  подписчиков и опросов становится вдвое, а `503` при переполнении считается
  отдельно на каждой реплике. Горизонтальное масштабирование требует общей шины
  (Mongo change streams на replica set или брокер), то есть выходит за рамки
  этого решения. Пока деплой — один инстанс.
- **Ошибка чтения не рушит поток.** Опрос логирует `Warn` один раз на серию
  ошибок и держит последний кадр: поток, который молчит, лучше потока, который
  врёт нулём. Восстановление пишет отдельное `Info`.
- **Запись доступа отдельная.** `withRequestLog` пишет `duration_ms` после
  возврата из хендлера, а у потока это время жизни соединения — часы в поле,
  где остальные маршруты кладут миллисекунды. Такой ответ получает
  `http.call.stream.finish` с `connection_ms` и без `duration_ms`. Признак —
  `Content-Type: text/event-stream`, который хендлер выставляет до `WriteHeader`;
  отказ `503` заменяет тип на `text/plain` и попадает в обычную запись.

## Проверка

```
go build ./...
go test ./internal/serverinfo/... ./internal/server/...
go vet ./internal/serverinfo/...
```

Юнит-тесты потока (`stream_test.go`):

- первый кадр содержит ровно `{"online":12,"max_online":100,"time":"Day 45 14:20"}`,
  второй приходит после записи нового документа;
- `": ping"` приходит без изменений;
- 1001-й подписчик получает `503` и `Retry-After: 10` и не попадает в hub;
- подписчик, который не читает, удаляется вместе с закрытием канала;
- отмена контекста запроса освобождает подписчика, горутины хендлеров
  возвращаются к базовому числу (`runtime.NumGoroutine` до и после).

Тест записи доступа (`httplog_test.go`) держит кадр доставленным до возврата из
хендлера через обёртки и проверяет, что запись — `http.call.stream.finish` без
`duration_ms`.

## Вне рамок

- История онлайна и графики: поток отдаёт текущее значение, не ряд.
- Изменения `proto/`: маршрут не-gRPC, схемы не трогаем.
- Ограничение по IP и авторизация: маршрут публичный, как два serverinfo-RPC.
- Замена `totalonline`/`worldtime`: их продолжают читать, пока лендинг не
  перейдёт на поток.
